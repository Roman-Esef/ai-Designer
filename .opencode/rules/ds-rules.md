# Дизайн-система IBP — правила работы (opencode)

Язык общения и комментариев в коде — русский.

## 1. Что за проект

ДС банковского enterprise-продукта (сделки, риски, обеспечения). **Ванильный
HTML/CSS, без React и без сборщика.** Экран — это один самодостаточный `.html`,
который открывается в браузере двойным кликом.

## 2. Карта репозитория

| Путь | Что там |
|---|---|

| `DS-IBP/specs/_index.md` | Манифест: компонент → спека → CSS → зависимости → версия |
| `DS-IBP/specs/_cheatsheet.md` | Чит-шит: по блоку на каждый компонент (классы, DOM-сниппет, инварианты). **Большой файл (~170 KB) — целиком не читать никогда** |

| `DS-IBP/scripts/docs-split.js` | Логика того же слоя: табы ↔ панели, локальный TOC, подсветка кода, свитчеры конструктора |

| `DS-IBP/templates/screen/Screen.html` | Стартовый шаблон экрана |

## 3. Как читать ДС и не сжечь контекст

Три команды закрывают 95 % задач:

```bash
# 1. Оглавление чит-шита — список всех компонентов (~50 строк)
grep -n "^## " DS-IBP/specs/_cheatsheet.md

# 2. Блок одного компонента (классы + готовый DOM-сниппет), 20–40 строк
sed -n '/^## Tile$/,/^## /p' DS-IBP/specs/_cheatsheet.md

# 3. Полная спека — только если блока не хватило (сложное поведение)
cat DS-IBP/specs/Tile.md
```

Если `sed` недоступен, возьми номер строки из команды 1 и прочитай файл
инструментом `read` с `offset`/`limit`.

**CSS компонентов (`DS-IBP/styles/*.css`) читать не нужно** — все классы и разметка уже
есть в чит-шите. Исключение — ищешь конкретный токен: `grep -n "имя-токена" DS-IBP/styles/*.css`.

## 4. Жёсткие запреты

- **Не читать `DS-IBP/scripts/icons-data.js`** — 671 KB в одну строку, разрушает контекст.
  Имена глифов брать только из `DS-IBP/specs/Icons.md`.
- **Не читать `DS-IBP/specs/_cheatsheet.md` целиком** и не читать страницы `DS-IBP/pages/**/*.html`
  целиком — только точечно (`grep`, `sed -n`, `read` с offset).
- **Не выдумывать значения.** Цвет, размер, отступ, радиус, тень, начертание —
  только `var(--токен)` и классы ДС. Нет подходящего — спросить у человека.
- **Не инлайнить SVG.** Иконка на экране — только `<i data-icon="имя"></i>`.
- **Не переверстывать внутренности компонента.** Разметка слотов берётся из
  чит-шита дословно: где показан `<svg>` — там `<svg>`, где `<span>` — `<span>`.
- **Не переопределять состояния компонентов извне.** Состояния (`--selected`/`--disabled`/`--open`/`:hover`/`[aria-current]`/`[aria-disabled]` и т.п.) задаёт только сам компонент. Собственный `<style>` экрана/страницы — только раскладка (grid/flex/gap) на токенах; в нём не должно быть селекторов, перекрывающих состояния по специфичности (пример: `button.<класс> { background:none }` перебивает `.<класс>--selected { background }` — пропадает подложка выделения). Разметку и состояние компонента брать из чит-шита/спеки дословно, состояние задавать данными (как `itemHTML` из `it.selected`), а не параллельными классами. Сброс браузерных дефолтов — только без задевания состояний. (Инцидент: NavPanel RND, 01.09.2026.)
- **Не создавать React-компоненты** (`.jsx`, `.tsx`, `.d.ts`) и не подключать их.
- **Не менять файлы ДС** (`DS-IBP/styles/`, `DS-IBP/scripts/`, `DS-IBP/specs/`, `DS-IBP/pages/` кроме
  `Projects/test/`) без явной просьбы человека. Это касается и страниц
  документации (`DS-IBP/pages/**`) и добавления новых файлов в `DS-IBP/styles/`/`DS-IBP/scripts/`
  (например, общего слоя `docs-split`): только по явному поручению.
- **Не трогать `DS-IBP/uploads/`** — это референсы пользователя.
- **Нет компонента в ДС — не изобретать его на ходу.** Остановиться, назвать
  недостающее, спросить. Отсутствие компонента — это находка, а не препятствие.

## 5. Обязательный каркас экрана

Любой экран из `Projects/test/` подключает ровно два внешних файла:

```html
<link rel="stylesheet" href="../../DS-IBP/ds.css">
...
<script src="../../DS-IBP/scripts/ds.js"></script>
```

Путь — **два уровня вверх + `DS-IBP/`** (`../../DS-IBP/`), потому что экран
лежит в `Projects/test/`, а дизайн-система — в соседней папке `DS-IBP/`.
Поштучно `DS-IBP/styles/*.css` и `DS-IBP/scripts/ds-*.js` не подключать:
`ds.js` сам догружает все рантаймы в правильном порядке, каждый молча ничего не
делает, если своей разметки на странице нет.

Собственный `<style>` экрана содержит **только раскладку** (grid, flex, gap) и
только на токенах. Ни одного `#hex`, ни одного «px на глаз» вне сетки.

`ds.js` оживляет компоненты сам — поповеры, модалки, аккордеоны, сортировку
таблицы, табы, тултипы, сворачивание панели навигации — при условии, что в
разметке стоят их хуки (`data-table`, `data-modal`, `data-tabs`, `data-popover`,
`data-riskmetric` и т.д.). **Свой JavaScript вместо рантайма ДС не пишется.**
Таблица хуков — `.opencode/skills/screen-assembly/references/runtime-hooks.md`.

## 7. Обращение с неизвестным

Назначение поля, смысл термина предметной области, связь между сущностями,
что означает статус — **спрашивать**, не достраивать догадкой. Выведенная догадка
неотличима от факта и оседает в документации как факт.

## 8. Работа с файлами: кодировка и временные копии

- Файлы репозитория — **UTF-8**. Кириллический контент читать и писать только
  через явный UTF-8: `[System.IO.File]::ReadAllText/WriteAllText` с
  `UTF8Encoding($false)`. `Get-Content`/`Set-Content` в PowerShell 5.1 портят
  UTF-8 без BOM (читают как ANSI) — появляются «не совпадающие» строки,
  словари, ключи, которые выглядят одинаково, а на деле разные.
- Временные диагностические копии страниц — только в `%TEMP%\opencode` или
  рядом с оригиналом (в той же папке), с сохранением UTF-8. НЕ оставлять
  временные `.html`/`.css` в корне проекта и после проверки удалять.
- Копия в другую папку ломает относительные пути `../../styles` — копию делай
  в ту же папку, что и оригинал.
- **Скомпилированные артефакты витрины живут своими копиями** (`_ds_bundle.js`,
  `_ds_manifest.json`, standalone-экспорты). При изменении `*.page.js` страниц,
  включённых в витрину, их надо пересобрать компилятором тем же заходом; вручную
  не правятся. Компилятор недоступен — зафиксировать остаток в отчёте как
  известный (урок Л25), не выдавать за «обновлено».

## 9. Проверка раскладки (статическая, без браузера)

- Модель opencode **не читает изображения** — скриншоты бесполезны.
- **Запуск браузера по скрипту (headless) в контуре компании не согласуется** —
  кибербезопасность. Ничего из ревью-флоу не должно зависеть от браузера:
  никаких `--dump-dom`, `--screenshot`, авто-детекта Chrome в рабочих проверках.
- Замена скриншотной проверки — **статический сенсор `layout-check`**
  (`.opencode/skills/screen-review/tooling/layout-check.mjs`): чистый Node,
  без рендера. Кодирует механические блокеры (Б1–Б16) и геометрию (K1–K6):
  токены берёт из `DS-IBP/styles/*.css`, ширину текста оценивает эвристикой
  (~8px/символ body-m). Вердикт FAIL — дефекты с номерами строк.
- **Честное ограничение статики:** без рендера не ловятся сломанная
  flex-цепочка и фактический overflow. Компенсация — марковочные правила
  (environment constraints): скролл-контейнер обязан
  `flex:1; min-height:0; overflow-y:auto` (К3), никаких фиксированных ширин
  на блоках сетки (Б10), зазоры — только компонентами (Б16). Что нельзя
  измерить — делаем структурно невозможным.
- Метрики, зависящие от ширины текста (K1, K2.1), — оценки по эвристике;
  при значении, близком к порогу, `layout-check` выводит «проверить вручную».
- `docs-split.mjs verify` (headless-живость) остаётся **локальным**
  инструментом раскатки там, где браузер установлен; в контуре компании
  используется только `check` (статическая структура). На ревью-флоу экранов
  он не влияет.

## 10. file:// — страницы открываются двойным кликом

- Не полагаться на `@import` внутри CSS по `file://` — нужные `DS-IBP/styles/*.css`
  подключать **явными `<link>`** на странице.
- `fetch`/XHR по `file://` с не-ASCII путём **не работает** — любые данные для
  рантайма (код во вкладке «Код» и т.п.) вставлять статично в страницу
  (`<script type="text/plain">`), не подгружать.
- Порядок скриптов на странице документации: рантаймы (`ds-*.js`) → `page.js`
  страницы → `docs-split.js`. Инлайн-обработчик, читающий состояние рантайма
  в момент события, срабатывает раньше (регистрируется при парсинге) и читает
  устаревшее значение. Переключение табов — по `data-`-атрибуту кнопки,
  клавиатура — через `setTimeout(0)`.

## 11. Страницы документации (`DS-IBP/pages/**`) — сценарий «docs-split»

- Страницы документации компонентов — отдельный сценарий, не Projects/test-экраны.
  Реструктуризация под паттерн «сплиттер + табы» и любые правки `DS-IBP/pages/**` —
  только по явному поручению человека.
- Общий слой паттерна: `DS-IBP/styles/docs-split.css` (все правила префиксованы
  `main.ds-split` — на страницы без класса не влияют) + `DS-IBP/scripts/docs-split.js`
  (активируется только при наличии `main.ds-split`). Страница-хост ставит
  класс `ds-split` на `main.page`.
- Структура: `main.page.ds-split` > `.splitpane--h[data-splitter]` > (панель A:
  демо `#pg-stage`; `.spl--h`; панель B: `.tabs[data-tabs]` + `.tabs-body` >
  три `.tabpane`). **Документация / Конструктор / Код используют единый
  контейнер `.docs-layout`** (центрированный, контент ~1200px; у документации
  справа колонка TOC) — вёрстка под табами идентична, никаких параллельных
  `.constructor-panel`/`.code-panel-wrap` с другими отступами.
- **Конвенция конструктора — две колонки:** справа (`.toggles`) —
  свитчеры, чекбоксы, радиобаттоны и слайдеры; слева (`.ctl-col`) —
  выпадающие списки и прочие инпуты. Если в конструкторе только один тип
  контролов — он встаёт в левую колонку. Контролы, разбитые на группы
  (`.ctl-group`, как в TableCell: «Шапка колонки», «Ячейка», «Строка»),
  сохраняют группировку — правила действуют отдельно внутри каждой группы.
  Свитчеры — самодостаточная подпись **без отдельного лейбла сверху**
  (правило компонента Switch) и **статичная**: не меняется от положения
  свитча — свитч называет опцию действием в On-состоянии («Показывать
  проценты»), а не переименовывается при выключении («Скрыть проценты»).
  Словарь `window.DS_SPLIT_SWITCH_LABELS` = статичная строка
  (`'Тултип': 'Показывать тултип'`) или объект `{ label, on? }` — `on` для
  явного on-значения селекта, когда эвристика даёт неверное направление.
  **НЕ конвертировать `select` в SegmentControl** — в конструкторе им
  не место; слайдер/range — обычная ячейка правой колонки, не на всю
  ширину (без `ctl--span`).
- **Запрет `.splitpane--app`** на панелях паттерна: его правило переводит
  панели в `display:block` и ломает flex-раскладку (скролл, центрирование,
  якоря). На панелях — `display:flex!important`.
- Вкладка «Код»: исходники статично в `<script type="text/plain" id="src-code-*">`
  (HTML — эталон из спеки, CSS — полный файл, JS — выжимка API из `page.js`);
  подсветка — общим скриптом.
- Локальный TOC (замена `ds-toc.js`) собирается `docs-split.js` из
  `section.section` внутри `#pane-docs`. `ds-toc.js`/`ds-toc.css`/`pg-kit.js`
  на страницах паттерна не подключаются.

## 12. Раскатка docs-split: тулчейн и правила чтения

- Раскатку ведёшь через тулчейн
  `.opencode/skills/docs-split/tooling/docs-split.mjs` (процедура — скилл
  `docs-split`), подкоманды:
  - `map` — перегенерировать карту `references/pages-index.md`;
  - `inject <page> [--css DS-IBP/styles/x.css]` — вставить **полный** CSS компонента
    в `src-code-css` (CSS не читать и не перепечатывать — это делает скрипт);
    **обязательный шаг ПОСЛЕ любой правки `styles/*.css` компонента раскатанной
    страницы** — ручная правка файла без `inject` оставляет вкладку «Код» со
    старым CSS (урок Л24);
  - `check <page>` — баланс тегов, остатки `ds-toc`/`pg-kit`, `.splitpane--app`,
    один `</body></html>`, три `src-code`-блока, panes;
  - `verify <page>` — headless-проверка живости (temp-копия кладётся в ту же
    папку, после прогона удаляется скриптом).
- **Читать страницы точечно**: head (`<link>`), `<style>`, секцию конструктора,
  футер, хвост скриптов — `grep`-ом по якорям + `read` с `offset/limit`.
  Docs-секции (Usage…Backlog) при раскатке не меняются — их не читать.
- Эталон структуры — `.opencode/skills/docs-split/references/skeleton.md`,
  а не готовая страница целиком (Entity.html и др. не перечитывать).
- Перед раскаткой и после — сверяться с картой `pages-index.md` (статус,
  тип конструктора, демо-хост, page.js, css-маппинг).
- Приёмка — `screen-reviewer` обычным порядком; ревьюеру давать скоп из карты,
  а не «прочитай страницу целиком».
