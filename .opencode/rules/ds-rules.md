# Дизайн-система IBP — правила работы (opencode)

Язык общения и комментариев в коде — русский.

## 1. Что за проект

ДС банковского enterprise-продукта (сделки, риски, обеспечения). **Ванильный
HTML/CSS, без React и без сборщика.** Экран — это один самодостаточный `.html`,
который открывается в браузере двойным кликом.

## 3. Как читать ДС и не сжечь контекст

Три команды закрывают 95 % задач:

```bash
# 1. Оглавление чит-шита — список всех компонентов (~50 строк)
grep -n "^## " DS-IBP/specs/_cheatsheet.md

# 2. Блок одного компонента (классы + готовый DOM-сниппет), 20–40 строк
sed -n '/^## Tile$/,/^## /p' DS-IBP/specs/_cheatsheet.md

# 3. Полная спека — только если блока не хватило (сложное поведение)
cat DS-IBP/specs/Tile.md
```

Если `sed` недоступен, возьми номер строки из команды 1 и прочитай файл
инструментом `read` с `offset`/`limit`.

**CSS компонентов (`DS-IBP/styles/*.css`) читать не нужно** — все классы и разметка уже
есть в чит-шите. Исключение — ищешь конкретный токен: `grep -n "имя-токена" DS-IBP/styles/*.css`.

## 4. Жёсткие запреты

- **Не читать `DS-IBP/scripts/icons-data.js`** — 671 KB в одну строку, разрушает контекст.
  Имена глифов брать только из `DS-IBP/specs/Icons.md`.
- **Не читать `DS-IBP/specs/_cheatsheet.md` целиком** и не читать страницы `DS-IBP/pages/**/*.html`
  целиком — только точечно (`grep`, `sed -n`, `read` с offset).
  **Исключение — страница-правило.** Страница, на которую ссылаются как на
  ИСТОЧНИК ТРЕБОВАНИЙ, а не как на документацию компонента, читается целиком —
  грепом она не заменяется: греп находит то, что уже знаешь, и молчит о том,
  чего не знаешь. Сегодня такая одна: `pages/patterns/LocalComponents.html`
  (правила локальных компонентов). Запрет здесь про бюджет окна, а бюджет —
  не основание работать по догадкам: план локального компонента, собранный
  без чтения этой страницы, пришлось переделывать целиком (20.09.2026).
- **Не выдумывать значения.** Цвет, размер, отступ, радиус, тень, начертание —
  только `var(--токен)` и классы ДС. Нет подходящего — спросить у человека.
- **Цвет иконки по умолчанию — `var(--secondary)`**, если компонент ДС, ТЗ или
  человек не задают иной. Иконку компонента ДС красит сам компонент — снаружи
  цвет не переопределяется; компонент, у которого иконка по умолчанию другого
  цвета, — вопрос к ДС, а не правка на экране (решение человека 22.09.2026;
  ReadOnlyField приведён в 1.009).
- **Не инлайнить SVG.** Иконка на экране — только `<i data-icon="имя"></i>`.
- **Не переверстывать внутренности компонента.** Разметка слотов берётся из
  чит-шита дословно: где показан `<svg>` — там `<svg>`, где `<span>` — `<span>`.
- **Не переопределять состояния компонентов извне.** Состояния (`--selected`/`--disabled`/`--open`/`:hover`/`[aria-current]`/`[aria-disabled]` и т.п.) задаёт только сам компонент. Собственный `<style>` экрана/страницы — только раскладка (grid/flex/gap) на токенах; в нём не должно быть селекторов, перекрывающих состояния по специфичности (пример: `button.<класс> { background:none }` перебивает `.<класс>--selected { background }` — пропадает подложка выделения). Разметку и состояние компонента брать из чит-шита/спеки дословно, состояние задавать данными (как `itemHTML` из `it.selected`), а не параллельными классами. Сброс браузерных дефолтов — только без задевания состояний. (Инцидент: NavPanel RND, 01.09.2026.)
- **Не создавать React-компоненты** (`.jsx`, `.tsx`, `.d.ts`) и не подключать их.
- **Не менять файлы ДС** (`DS-IBP/styles/`, `DS-IBP/scripts/`, `DS-IBP/specs/`, `DS-IBP/pages/`;
  экраны агента живут в `Concepts/`) без явной просьбы человека. Это касается и страниц
  документации (`DS-IBP/pages/**`) и добавления новых файлов в `DS-IBP/styles/`/`DS-IBP/scripts/`
  (например, общего слоя `docs-split`): только по явному поручению.
- **Не трогать `DS-IBP/uploads/`** — это референсы пользователя.
- **Нет компонента в ДС — не изобретать его на ходу.** Остановиться, назвать
  недостающее, спросить. Отсутствие компонента — это находка, а не препятствие.

## 5. Обязательный каркас экрана

Любой экран из `Concepts/<Имя>/` подключает ровно два внешних файла плюс фавикон:

```html
<link rel="icon" type="image/svg+xml" href="../../DS-IBP/assets/logo.svg">
<link rel="stylesheet" href="../../DS-IBP/ds.css">
...
<script src="../../DS-IBP/scripts/ds.js"></script>
```

Фавикон — логотип ДС (`DS-IBP/assets/logo.svg`, векторный, подключается как есть,
без растеризации). Ставится в `<head>` перед `<link rel="stylesheet">`, путь —
тот же относительный уровень до `DS-IBP/`, что и у `ds.css`. Обязателен на любой
странице проекта и концепта: и в `Concepts/**`, и в `Projects/**` (добавлено
05.09.2026 по просьбе человека).

**Projects и Concepts.** В `Projects/` — только файлы, соответствующие
настоящей системе, строго на компонентах ДС. В `Concepts/` — концепты: по
умолчанию тоже строго на ДС; кастомное решение — только когда ТЗ прямо его
просит. Проверки для обеих папок одинаковые: осознанное отклонение по ТЗ
записывается в «Открытые вопросы и допущения» спеки, и красный сенсор на нём
ожидаем — это не повод молча переписать экран на ДС и не повод гасить
правило. Песочница `Projects/test/` удалена 15.09.2026 — её заменяют концепты
(решение человека).

**Хаб проектов.** Корневой `index.html` строит меню и три колонки (Дизайн-система
· Проекты · Концепты) из реестра `hub.js`. Новый проект или концепт
регистрируется записью в `hub.js` (`group`, `href` и `root` от корня; `root`
лежит в папке своей группы) — иначе его нет на хабе, а любой `.html` в
`Projects/` или `Concepts/` вне `root` записи краснит гейт. В экранах проектов и
концептов строка пользователя в футере меню (`<a class="nav__user">`) ведёт на
хаб: `href` — относительный путь до корневого `index.html`,
`aria-label="Хаб проектов"`; футер из `IBPHome.footerHTML(...)` подменяется в
экранном скрипте через `.replace(...)`. Оба правила ловит сторож
`projects-hub.mjs` (коды П1–П5, шаг гейта `projects`). Из документации ДС на хаб
ведёт закреплённый низ левой панели (`ds-nav.js`). Добавлено 15.09.2026 по
просьбе человека.

Путь — **два уровня вверх + `DS-IBP/`** (`../../DS-IBP/`), потому что экран
лежит в `Concepts/<Имя>/`, а дизайн-система — в соседней папке `DS-IBP/`.
Поштучно `DS-IBP/styles/*.css` и `DS-IBP/scripts/ds-*.js` не подключать:
`ds.js` сам догружает все рантаймы в правильном порядке, каждый молча ничего не
делает, если своей разметки на странице нет.

Собственный `<style>` экрана содержит **только раскладку** (grid, flex, gap) и
только на токенах. Ни одного `#hex`, ни одного «px на глаз» вне сетки.

**Высота главной таблицы.** Если на странице одна таблица — или она основной
контентный блок (реестр) — она занимает **всю свободную высоту экрана** за
вычетом полей контента, крошек, шапки страницы и тулбара/фильтра таблицы. Это
делается классами ДС, а не своим `<style>`: на рабочую область ставится
`.screen--app` (Layout, вариант app-shell — фикс. вьюпорт `height:100vh`,
`overflow:hidden`, `.screen__content` получает `min-height:0`), на таблицу —
`.dtable--fill` (Table): тело таблицы скроллится внутри, крошки/шапка/тулбар/
пагинация закреплены. Если над/под таблицей есть тайлы — кейс индивидуальный, но
по умолчанию таблица всё равно занимает оставшуюся высоту (та же пара классов).

`ds.js` оживляет компоненты сам — поповеры, модалки, аккордеоны, сортировку,
изменение ширины и перетаскивание колонок таблицы, табы, тултипы, сворачивание
панели навигации — при условии, что в разметке стоят их хуки (`data-table`,
`data-modal`, `data-tabs`, `data-popover`, `data-riskmetric` и т.д.). **Свой
JavaScript вместо рантайма ДС не пишется.**
Таблица хуков — `.opencode/skills/screen-assembly/references/runtime-hooks.md`.

## 6. Каталог компонентов

**Основы:** Colors · Typography · Spacing (сетка 12 колонок) · Radius · Elevation · Icons · Illustrations · Layout (каркас экрана)

**Атомы:** Avatar · Badge · Buttons · Checkbox · Chip · Divider · IconButton · LabelHelper · Link · ProgressBar · Radiobutton · Skeleton · Spinner · Switch

**Молекулы:** Alert · Breadcrumbs · ButtonGroup · ContextMenu · DatePicker · DropdownList · EmptyState · InputAmountRange · InputAutocomplete · InputDate · InputDateRange · InputText · NavTile · Pagination · ReadOnlyField · SegmentControl · Splitter · SubTab · Tab · Toast · Tooltip

**Организмы:** AllocationBar · Chart · Drawer · Entity · Kanban · Modal · NavPanel · PageHeader · Popover · RiskMetric · SnackBar · Table · TableCell · TableFilter · Tile

**Созависимые части (собираются вместе, как чип+поповер у RiskMetric):**
- **TableFilter** — кнопка «Фильтр» и модалка фильтра `.tfm` неотъемлемы: собираешь фильтр — собираешь и модалку (`.tfm__nav` + `.tfm__panel` + `.tfm__sec` + `.tfm__grid`). Структура — ДС, данные (какие секции/поля/пресеты) — потребитель. Вторичная кнопка подвала — «Очистить фильтр», не «Очистить». Собственный CSS на форму фильтра не пишется.
- **LabelHelper — часть поля, а не компонент страницы.** Лейбл и хелпер не ставятся на экран сами по себе: своего контейнера у них нет, и вне родителя их не опознать. Их приносит с собой родитель — InputText, InputAutocomplete, InputDate, ReadOnlyField, Checkbox, Radiobutton, Switch, DropdownList. Отсюда следствие для документации: **в списках «из чего собрано» и в поле `ds` паспорта LabelHelper отдельной строкой не числится** — там перечисляются компоненты, которые видно на экране как самостоятельные единицы. Тот же порядок у любой части, которая существует только внутри родителя. Правило компонента — LabelHelper 1.007, решение человека 22.09.2026.
- **SubTab — только под Tab, и только внутри него.** Табы второго уровня (`.subtabs` / `.subtab`) применяются **исключительно на экране, где есть ряд табов первого уровня** (`.tabs--horiz` с `.tab`), и размещаются **как содержимое одного из табов первого уровня** — под его рядом, а не отдельной панелью экрана. Одиночный `.subtabs` без первого уровня — дефект: механика заливки сама по себе не сообщает, что уровень подчинённый, и экран читается как один уровень навигации с необычным видом. Нужен одиночный ряд переключения вьюх — это **Tab**; нужен выбор значения параметра (период, единицы, режим показа) — **SegmentControl**. **Размер — в пару к первому уровню и не крупнее его.** Шкала общая с Tab: `.subtabs--m` 40 · `.subtabs--s` 32 · `.subtabs--xs` 24 (без класса — S). Рекомендованный выбор — шаг вниз: `.tab--m` → `.subtabs--s`, `.tab--s` → `.subtabs--xs`. Равный размер допустим, когда второй уровень — главный переключатель экрана. Второй уровень **крупнее** первого — инверсия иерархии, запрещено. Эту половину правила линтер НЕ стережёт — сверять на приёмке. Ёмкость ряда — **2–5 пунктов**: переполнения у компонента нет by design (трек не переносится и не скроллится), 6+ подразделов собираются на `.tab--s` + `.tabs--bare`. Ловится линтером, правило `B14` (BLOCKER).

## 7. Обращение с неизвестным

Назначение поля, смысл термина предметной области, связь между сущностями,
что означает статус — **спрашивать**, не достраивать догадкой. Выведенная догадка
неотличима от факта и оседает в документации как факт.

## 8. Работа с файлами: кодировка и временные копии

- Файлы репозитория — **UTF-8**. Кириллический контент читать и писать только
  через явный UTF-8: `[System.IO.File]::ReadAllText/WriteAllText` с
  `UTF8Encoding($false)`. `Get-Content`/`Set-Content` в PowerShell 5.1 портят
  UTF-8 без BOM (читают как ANSI) — появляются «не совпадающие» строки,
  словари, ключи, которые выглядят одинаково, а на деле разные.
- Временные диагностические копии страниц — только в `%TEMP%\opencode` или
  рядом с оригиналом (в той же папке), с сохранением UTF-8. НЕ оставлять
  временные `.html`/`.css` в корне проекта и после проверки удалять.
- Копия в другую папку ломает относительные пути `../../styles` — копию делай
  в ту же папку, что и оригинал.
- **Код с регулярными выражениями и escape-последовательностями не пишется
  через шелл** — только файловым редактором. Шелл-слой схлопывает `\\` в `\`
  даже внутри закавыченного heredoc (bash и python — слой один и тот же):
  `\s` доезжает как `s`, юникод-escape кириллической буквы превращается
  в саму букву ещё до записи.
  Итог — синтаксически валидная регулярка, которая молча находит ноль
  совпадений (уроки Л51, Л73, класс Л33). Если правка не делается редактором
  на месте — записать вставку отдельным файлом (редактором) и срастить
  скриптом, который только читает и склеивает.
  После записи любого сторожа — прогон, подтверждающий **непустой** результат
  на заведомо подходящих данных: «ошибок нет» не равно «работает».
- **Код выхода снимается отдельной командой сразу после проверяемой**, без
  подстановок и пайпов в той же строке: `cmd > /dev/null 2>&1; echo $?`.
  В `echo "$(basename $f) — код $?"` подстановка выполняется первой и
  перезаписывает `$?`; в `cmd | tail` код принадлежит `tail`. Замер соврёт,
  а отчёт «шаг выполнен, код 0» станет фикцией — ровно то, что запрещает
  Л37 (урок Л52).
  **Что делать вместо этого в цикле по файлам:** код выхода не снимать вовсе —
  читать строку вердикта, её печатает сам инструмент: `ВЕРДИКТ:` у сенсора,
  `BLOCKER n · WARN n` у линтера. Запрет без замены не работает: это правило
  уже стояло здесь, с этим самым примером `$(basename $f)`, и было нарушено
  в тот же день (урок Л68).
- **Скомпилированные артефакты витрины в репозитории не хранятся.** Бандл
  `_ds_bundle.js` и манифест `_ds_manifest.json` были производными внешнего
  инструмента: ни одна страница их не подключала, линтер и сенсоры их не
  читали, локального компилятора не существует. Удалены 04.09.2026. Не
  собирать, не воссоздавать, не сверять с ними `*.page.js`; расхождения
  больше нет и в отчётах оно не фиксируется (урок Л25 закрыт). Маркер
  `<!-- @dsCard … -->` первой строкой страницы остаётся — его требует
  линтер (C1).

## 9. Проверка раскладки (статическая, без браузера)

- **Изображения:** вложение картинки в сообщение до модели не доходит, а файл
  изображения, прочитанный инструментом `read` с диска, модель видит — проверено
  23.09.2026 на рабочей модели. Визуальная сверка возможна: скриншот кладётся
  файлом в папку проекта и читается как файл, а не вложением. Способ зависит от
  модели и провайдера контура — проверка на своей машине: прочитать файл и
  спросить, что на нём.
- **Запуск браузера по скрипту (headless) в контуре компании не согласуется** —
  кибербезопасность. Ничего из ревью-флоу не должно зависеть от браузера:
  никаких `--dump-dom`, `--screenshot`, авто-детекта Chrome в рабочих проверках.
- Замена скриншотной проверки — **статический сенсор `layout-check`**
  (`.opencode/skills/screen-review/tooling/layout-check.mjs`): чистый Node,
  без рендера. Кодирует часть механических блокеров и геометрии; **фактический
  состав печатает сам сенсор** — `layout-check.mjs --rules`, перечислять его
  здесь прозой нельзя (копия разъезжается с кодом, урок Л43).
  Токены берёт из `DS-IBP/styles/*.css`, ширину текста оценивает эвристикой
  (~8px/символ body-m). Вердикт FAIL — дефекты с номерами строк.
- **Честное ограничение статики:** без рендера не ловятся сломанная
  flex-цепочка и фактический overflow. Компенсация — марковочные правила
  (environment constraints): скролл-контейнер обязан
  `flex:1; min-height:0; overflow-y:auto` (К3), никаких фиксированных ширин
  на блоках сетки (Б10), зазоры — только компонентами (Б16). Что нельзя
  измерить — делаем структурно невозможным.
- Метрики, зависящие от ширины текста (K1, K2.1), — оценки по эвристике;
  при значении, близком к порогу, `layout-check` выводит «проверить вручную».
- У `docs-split.mjs` только статическая проверка `check`. Браузерная
  подкоманда `verify` и её харнесс удалены 13.09.2026: в контуре компании её
  нельзя выполнить, а правило, ссылающееся на недоступный инструмент, даёт
  фиктивное «выполнено» или вечно красный гейт (класс урока Л37).

## 10. file:// — страницы открываются двойным кликом

- Не полагаться на `@import` внутри CSS по `file://` — нужные `DS-IBP/styles/*.css`
  подключать **явными `<link>`** на странице.
- `fetch`/XHR по `file://` с не-ASCII путём **не работает** — любые данные для
  рантайма (код во вкладке «Код» и т.п.) вставлять статично в страницу
  (`<script type="text/plain">`), не подгружать.
- Порядок скриптов на странице документации: рантаймы (`ds-*.js`) → `page.js`
  страницы → `docs-split.js`. Инлайн-обработчик, читающий состояние рантайма
  в момент события, срабатывает раньше (регистрируется при парсинге) и читает
  устаревшее значение. Переключение табов — по `data-`-атрибуту кнопки,
  клавиатура — через `setTimeout(0)`.

## 11. Страницы документации (`DS-IBP/pages/**`) — сценарий «docs-split»

- Страницы документации компонентов — отдельный сценарий, не экраны из Concepts/ или Projects/.
  Реструктуризация под паттерн «сплиттер + табы» и любые правки `DS-IBP/pages/**` —
  только по явному поручению человека.
- Общий слой паттерна: `DS-IBP/styles/docs-split.css` (все правила префиксованы
  `main.ds-split` — на страницы без класса не влияют) + `DS-IBP/scripts/docs-split.js`
  (активируется только при наличии `main.ds-split`). Страница-хост ставит
  класс `ds-split` на `main.page`.
- Структура: `main.page.ds-split` > `.splitpane--h[data-splitter]` > (панель A:
  демо `#pg-stage`; `.spl--h`; панель B: `.tabs[data-tabs]` + `.tabs-body` >
  три `.tabpane`). **Документация / Конструктор / Код используют единый
  контейнер `.docs-layout`** (центрированный, контент ~1200px; у документации
  справа колонка TOC) — вёрстка под табами идентична, никаких параллельных
  `.constructor-panel`/`.code-panel-wrap` с другими отступами.
- **Конвенция конструктора — две колонки:** справа (`.toggles`) —
  свитчеры, чекбоксы, радиобаттоны и слайдеры; слева (`.ctl-col`) —
  ButtonGroup, выпадающие списки и прочие инпуты. Если в конструкторе только один тип
  контролов — он встаёт в левую колонку. Контролы, разбитые на группы
  (`.ctl-group`, как в TableCell: «Шапка колонки», «Ячейка», «Строка»),
  сохраняют группировку — правила действуют отдельно внутри каждой группы.
  Свитчеры — самодостаточная подпись **без отдельного лейбла сверху**
  (правило компонента Switch) и **статичная**: не меняется от положения
  свитча — свитч называет опцию действием в On-состоянии («Показывать
  проценты»), а не переименовывается при выключении («Скрыть проценты»).
  Словарь `window.DS_SPLIT_SWITCH_LABELS` = статичная строка
  (`'Тултип': 'Показывать тултип'`) или объект `{ label, on? }` — `on` для
  явного on-значения селекта, когда эвристика даёт неверное направление.
  **Выбор по числу вариантов (решение человека 21.09.2026):** да/нет —
  свитч; 2–3 равноправных варианта («Юрлицо / Физлицо», «Найдено /
  Выбрано») — ButtonGroup с сегментированным выбором; 4 и больше —
  выпадающий список. Страница пишет все выборы селектами, превращает их
  `docs-split.js`: свитчем становится селект из словаря
  `DS_SPLIT_SWITCH_LABELS` или с вариантом «выключено» (`no`/`off`/
  `none`/«Нет»), остальные на 2–3 варианта — ButtonGroup (outline,
  fullwidth, M) в левой колонке. **ButtonGroup — тоже без лейбла
  сверху** (правило компонента ButtonGroup, 21.09.2026): слой прячет
  `.lbl`, его текст уходит в `aria-label` группы, поэтому варианты
  селекта пишутся самодостаточными — «1 чип / 2 чипа / 3 чипа», «По
  левому краю / По правому краю», «Без легенды», а не «1 / 2 / 3»,
  «Слева / Справа», «Нет». Свитч, управляющий полем, стоит в `.ctl`
  первым и несёт имя опции («Prefix»), а поле под ним — свой `.lbl`
  по смыслу («Пример», «Вариант»): лейбл над свитчем — дефект (R9).
  **SegmentControl в конструкторе не используется.** Пустая колонка не рисуется (`docs-split.css`) —
  единственная оставшаяся встаёт слева. Слайдер/range — обычная ячейка
  правой колонки, не на всю ширину (без `ctl--span`).
- **Запрет `.splitpane--app`** на панелях паттерна: его правило переводит
  панели в `display:block` и ломает flex-раскладку (скролл, центрирование,
  якоря). На панелях — `display:flex!important`.
- Вкладка «Код»: исходники статично в `<script type="text/plain" id="src-code-*">`
  (HTML — эталон из спеки, CSS — полный файл, JS — выжимка API из `page.js`);
  подсветка — общим скриптом.
- Локальный TOC (замена `ds-toc.js`) собирается `docs-split.js` из
  `section.section` внутри `#pane-docs`. `ds-toc.js`/`ds-toc.css`/`pg-kit.js`
  на страницах паттерна не подключаются.

## 12. Раскатка docs-split: тулчейн и правила чтения

- Раскатку ведёшь через тулчейн
  `.opencode/skills/docs-split/tooling/docs-split.mjs` (процедура — скилл
  `docs-split`), подкоманды:
  - `map` — перегенерировать карту `references/pages-index.md`;
  - `inject <page> [--css DS-IBP/styles/x.css]` — вставить **полный** CSS компонента
    в `src-code-css` (CSS не читать и не перепечатывать — это делает скрипт);
    **обязательный шаг ПОСЛЕ любой правки `styles/*.css` компонента раскатанной
    страницы** — ручная правка файла без `inject` оставляет вкладку «Код» со
    старым CSS (урок Л24);
  - `check <page>` — баланс тегов, остатки `ds-toc`/`pg-kit`, `.splitpane--app`,
    один `</body></html>`, три `src-code`-блока, panes.
- **Читать страницы точечно**: head (`<link>`), `<style>`, секцию конструктора,
  футер, хвост скриптов — `grep`-ом по якорям + `read` с `offset/limit`.
  Docs-секции (Usage…Backlog) при раскатке не меняются — их не читать.
- Эталон структуры — `.opencode/skills/docs-split/references/skeleton.md`,
  а не готовая страница целиком (Entity.html и др. не перечитывать).
- Перед раскаткой и после — сверяться с картой `pages-index.md` (статус,
  тип конструктора, демо-хост, page.js, css-маппинг).
- Приёмка — `screen-reviewer` обычным порядком; ревьюеру давать скоп из карты,
  а не «прочитай страницу целиком».

## 13. Экономия контекста (для всех агентов)

**Не резать инструктаж ради экономии.** Правила, скиллы и `AGENTS.md` — это
стабильный, переиспользуемый вход, который лежит в дешёвой категории
«cache hit». Сокращение инструктажа лишь растит «cache miss» (контекст
перестаёт повторяться — каждый запрос платит полную цену входа) и роняет
качество. Экономить надо там, где деньги реально большие: **output** и
**cache miss**, а не кэш-хит.

- **ДС читать только точечно** — команды из §3: `grep -n "^## "` по
  оглавлению чит-шита, `sed -n '/^## <Имя>$/,/^## /p'` по блоку компонента.
  Никаких `cat`/чтения целиком `_cheatsheet.md`, `icons-data.js`,
  страниц `pages/**`. Запрет и его единственное исключение (страница-правило)
  живут в §4 и здесь не пересказываются: правило с тремя владельцами
  расходится на первой же правке — исключение, дописанное в один пересказ,
  развело бы их (Л43).
- **Рекурсивные листинги `.opencode/` и `Skills/` не вываливать в диалог.**
  Дампы остаются в контексте и пересылаются в каждом следующем ходу. Вместо
  них — `glob`/`grep` по паттерну.
- **`read`/`sed` — с `offset`/`limit` по конкретным секциям**, не «от глаза»
  и не большие куски. Нужная секция — это 20–40 строк, а не весь файл.
- **В задание субагенту — пути + короткие утверждения**, не выжимки больших
  файлов. Субагент стартует с чистого контекста: простыня в задании — это
  раздутый input на его сессии (маршруты и формат — `ai-designer.md`).
- **Дефекты приёмки возвращать одним заданием**, не по одному (см.
  `ai-designer.md`, маршрут «Собери экран», шаг «Вердикт NEEDS-WORK»). Один
  round-trip вместо нескольких — это разница между кэш-хитом и полным входом.
- **Выводы команд обрезать до нужного.** Не выводить в чат лишние колонки и
  строки; `Select-Object -First/-Last` не использовать — при превышении лимита
  вывод и так уходит в файл, читать его через `read` с `offset/limit`.
- **Новая сессия — на новую задачу.** Чем длиннее сессия, тем дороже каждый
  следующий ход (контекст растёт, кэш-хит растёт). Задача закрыта — сессию
  закрыть, новую крупную задачу начинать в новой сессии.
  Контекст между сессиями переносит файл, а не история: закрывая задачу,
  ведущий агент пишет `Concepts/<Задача>/<Задача>.handoff.md` (команда `/handoff`
  — то же вручную посреди задачи), новая сессия начинается с `/resume <Задача>`.
  Внутри длинной задачи граница проходит **по этапу** (см. ниже «Бюджет окна»),
  а не по сжатию контекста: сжатие теряет детали принятых решений, файл — нет.
- **Проверки — одной командой в конце захода.** Во время работы — точечно
  (сенсор на своём экране, `verify --only <ID>` для своего сторожа); в конце —
  `lessons-cli gate`, он гоняет только сторожей изменившегося. Серия
  отдельных прогонов стоит ход агента и вывод в контексте на каждый.
- **Кураторская выжимка уроков читается, архив — нет.** `screen-review/references/lessons.md` —
  рабочий вход всех ролей; `screen-review/references/lessons-raw.md` (большой архив полной истории)
  открывается только при курации.

### Бюджет окна: смета до старта и границы этапа

Окно модели на рабочем контуре — около **250 000 токенов на сессию, вход и
выход вместе**. Правила выше экономят ход; эти — решают, влезет ли заход
целиком. Скилл — `session-plan` (`.opencode/skills/session-plan/SKILL.md`).

- **Смета считается до старта, а не по ощущению.**
  `node .opencode/skills/session-plan/tooling/ctx-budget.mjs --stage <этап> …`
  печатает `ВЕРДИКТ: OK | ВНИМАНИЕ | РАЗБИТЬ`. `РАЗБИТЬ` — заход идёт длинным
  маршрутом по этапам, состав печатает `--stages`.
- **Сессия закрывается на границе этапа**, а не когда стало тяжело: история
  пересылается целиком на каждом ходу, поэтому последний ход длинной сессии
  стоит в разы дороже первого, а ощущение «ещё влезет» приходит на два-три
  хода позже точки, где закрыться было дёшево.
- **Собранный экран целиком не перечитывается.** Правка — `grep -n` по якорю
  секции (`<!-- #sec:head -->`, `#sec:content`, `#sec:modals` в эталоне
  `screen-assembly/references/skeleton.html`) → `read` с `offset/limit` на
  20–40 строк → точечная правка. Замер: три круга правок на экране в 1486
  строк стоят 20 900 токенов по якорю против 96 700 с перечитыванием целиком —
  разница в 75 800 переводит заход из OK в РАЗБИТЬ.
- **Спека дописывается по разделам по мере сборки**, а не пишется целиком в
  конце: иначе этап-спека обязан перечитать весь HTML.
- **В спеке нет журнала правок.** `<Имя>.screen.md` описывает текущее
  состояние — как handoff, история живёт в git. Разделы вида
  «Правки ДД.ММ.ГГГГ» — блокер **Б32**. Цена нарушения замерена:
  в `Portfolio.screen.md` журнал занимал 59 % файла, ≈12 500 токенов, и их
  платила каждая сессия, которая открывала спеку.
- **Экран больше ~800 строк планируется длинным маршрутом** сразу, без попытки
  собрать одним заходом.

## 14. Самообучение

Заход, в котором что-то сломалось и починилось, заканчивается уроком с полем
**«Закрепление»** — во что этот урок превратился. Процедура целиком —
в скилле **`lessons`** (`.opencode/skills/lessons/SKILL.md`); здесь она не
пересказывается, чтобы копия не разошлась с оригиналом (урок Л43).

Что верно всегда:

- закрепление уровня «исполняемое» доказывается **откатом**
  (`lessons-cli verify`), а не наличием строки в файле;
- если дефект должен был поймать существующий сторож и не поймал — чинится
  **сторож**, а не пишется процедурное правило поверх;
- курация запускается **событием** (долг ≥ 3 по `lessons-cli state`), а не
  календарём: у агента нет часов и нет памяти между сессиями;
- заход закрывается командой `lessons-cli gate` — строка `ВЕРДИКТ:` идёт в
  отчёт;
- урок дописывается командой `lessons-cli add`, а форму записи — якорь,
  уровень закрепления, ярлыки полей — проверяет `lessons-cli check`. Блокер
  этой команды означает, что запись врёт, и чинится сразу.
