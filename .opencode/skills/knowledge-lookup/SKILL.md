# Поиск по базе знаний продукта

## Где она лежит

**База знаний — отдельный репозиторий, вне репозитория дизайн-системы.**
Внутри ДС её нет и не будет: ДС описывает интерфейс, база знаний — продукт и
пользователей. У них разный срок жизни и разные владельцы.

На момент написания скилла этот репозиторий ещё не создан. Путь к нему станет
известен позже и прописывается в **двух местах**:

1. `opencode.json` → `permission.external_directory` — разрешение читать вне
   рабочей директории;
2. этот файл, таблица «Карта репозитория» ниже — переменная `KB`.

```
KB = <путь не задан>
```

Больше нигде путь не зашит.

## Проверка первым делом

```bash
# подставь реальный путь вместо <KB>
ls <KB> 2>/dev/null || echo "база знаний недоступна"
```

Три исхода, и все три — штатные:

| Что видишь | Что это значит | Что делать |
|---|---|---|
| Список папок | всё работает | искать по карте ниже |
| `база знаний недоступна`, путь в скилле не задан | репозитория ещё нет | вернуть пустой отчёт (см. ниже) |
| `база знаний недоступна`, но путь задан | нет разрешения `external_directory` либо репозиторий не склонирован | **сообщить об этом в отчёте отдельной строкой** — это неисправность настройки, а не отсутствие данных |

**Пустой отчёт** — это когда все разделы пусты, а в «Чего в базе знаний нет»
одна строка: «Репозиторий базы знаний недоступен, исследовательская часть не
выполнена». Дальше работа продолжается по одному ТЗ, и это нормально.

Чего делать нельзя ни при каком исходе: искать обходные пути, пересказывать ТЗ
как исследование, реконструировать пользователей по интерфейсу или по коду
существующих экранов. Отсутствие данных — валидный результат, он показывает,
где нужны интервью. Выдуманные данные неотличимы от найденных и уедут в дизайн
требованием.

## Карта репозитория

Ожидаемая структура (уточнится, когда репозиторий появится):

| Папка | Что внутри |
|---|---|
| `<KB>/users/` | роли, портреты пользователей, объём на роль, контекст работы |
| `<KB>/jobs/` | задачи и цели пользователей (JTBD), сценарии, критерии успеха |
| `<KB>/business/` | задачи компании, метрики, приоритеты |
| `<KB>/constraints/` | ограничения: регламенты, техника, контур, интеграции |
| `<KB>/research/` | результаты исследований и интервью, файл на исследование |
| `<KB>/decisions/` | ранее принятые решения с датой и статусом |

Реальная раскладка важнее этой таблицы. Расходится — ориентируйся по факту:

```bash
find <KB> -name "*.md" | head -50
```

## Как искать

```bash
# 1. Что вообще есть
find <KB> -name "*.md" | sort

# 2. По теме — сначала по заголовкам, потом по тексту
grep -rn "^#.*сделк" <KB>/
grep -rln "реестр\|фильтр\|сортировк" <KB>/

# 3. Что относится к конкретной роли
grep -rln "риск-менеджер" <KB>/

# 4. Свежие решения
grep -rn "^date:\|^дата:\|обновлено" <KB>/decisions/
```

Файл нашёлся — читай целиком, они небольшие. Файлов больше пяти — сначала
заголовки (`grep -n "^#" файл.md`), потом только нужные разделы.

## Что считать источником, а что нет

| Источник | Статус |
|---|---|
| `<KB>/**` | база знаний, основной источник |
| ТЗ на конкретный экран | требование, не исследование. Цитировать можно, выдавать за вывод исследования — нет |
| Существующий экран или макет | свидетельство о том, как сделано **сейчас**, а не о том, как нужно |
| Спеки ДС (`DS-IBP/specs/`) | про интерфейс, не про пользователей |

## Правила

1. **Каждое утверждение — со ссылкой на файл.** Без ссылки утверждение не
   существует.
2. **Дата решает.** Два противоречащих решения — действует позднее, но
   упоминаются оба, а расхождение выносится отдельной строкой.
3. **Факт, гипотеза и мнение — разные вещи.** Помечай, что именно нашёл.
4. **Малая выборка.** На роль приходится 1–5 пользователей. Проценты и
   «большинство» запрещены — только «в интервью с <роль> прозвучало».
5. **Молчание базы — это ответ.** «Не нашлось» полезнее выдуманной уверенности.

## Приложение: как подключить репозиторий, когда он появится

Шаг 1. Разрешить чтение вне рабочей директории — `opencode.json`, ключ
`permission.external_directory` (сейчас пустой, это точка расширения):

```json
"external_directory": {
  "~/ibp-knowledge/**": "allow"
}
```

Путь пишется абсолютным или от домашней папки (`~` / `$HOME`). Относительные
пути вида `../ibp-knowledge` здесь не разворачиваются.

Шаг 2. Задать `KB` в начале этого файла — тем же путём.

Шаг 3. Проверить: `ls <KB>` из сессии opencode должен вернуть список папок.
Вернул отказ — не хватает разрешения из шага 1.

Опционально: запретить запись в базу знаний, чтобы агент точно её не изменил —

```json
"edit": {
  "~/ibp-knowledge/**": "deny"
}
```

## Приложение: требования к файлам базы знаний

Материалы читает не только человек, но и модель с небольшим окном контекста.

1. **Один файл — одна тема.** Десять коротких файлов лучше одного на 200 КБ.
2. **YAML-шапка обязательна** — по ней агент отбирает нужное, не читая тело:

   ```markdown
   ---
   type: research | user | job | constraint | decision | business
   title: Роли пользователей и FI-блок
   roles: [аналитик, риск-менеджер]
   date: "26.05.2026"
   status: действует | отменено | гипотеза
   source: интервью с 3 пользователями
   ---
   ```

3. **Дата в каждом файле** — по ней разрешаются противоречия.
4. **Факт, гипотеза и мнение помечаются явно.** Непомеченная гипотеза станет
   для агента фактом.
5. **Таблицы вместо прозы**, чёткие заголовки разделов.
6. **Никаких процентов при малой выборке.**
