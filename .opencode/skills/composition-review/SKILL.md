# Приёмка композиции

Два гейта не заменяют друг друга:

| Гейт | Что ловит |
|---|---|
| `screen-review` | механика ДС: классы, токены, хуки, суммы колонок, заглушки |
| **этот** | **композиция**: пустоты, перегруз, разнобой, неверная ширина, иерархия |

Экран может пройти `screen-review` полностью и при этом выглядеть плохо — именно
это здесь и проверяется. Правила и обоснования — в скилле `layout-composition`.

## Как проверять

**Скриншотной проверки нет** (контур компании — запуск браузера по скрипту не
согласуется, см. ds-rules.md §9). Композиция проверяется **статически**:

1. Прогони статический сенсор:
   `node .opencode/skills/screen-review/tooling/layout-check.mjs <путь к экрану>`
   Он считает ширины тайлов (`span N`), колонки полей (K5), строки и высоты
   (ритм 40px), пустоту у правой кромки (K1), длинные поля (K2/K2.1),
   сопоставимость соседей (K6) — токены берёт из `DS-IBP/styles/*.css`, ширину текста
   оценивает эвристикой (~8px/символ).
2. FAIL из layout-check — дефекты с номерами строк, переноси в отчёт.
   WARN и пометки «проверить вручную» — проверь глазами по исходнику:
   посчитай строки и пиксели по формулам ниже.
3. Сверь вывод с таблицей раскладки в `<Имя>.screen.md` (это K11).

### Считай в строках и пикселях, НЕ в полях

Число полей — обманчивая метрика: тайл с 11 полями в 3 колонки ниже, чем тайл
с 6 полями в одну. Меряй **строки** и высоту.

```
ширина контента   = ширина окна − 56 (rail) − 48 (поля 24×2)
ширина колонки    = (контент − 11×16) / 12
ширина тайла col-N = N×колонка + (N−1)×16
внутри тайла       = ширина тайла − 40   (--tile-pad-x 20×2)
ячейка сетки       = (внутри − (кол−1)×16) / кол

строк в тайле     = ceil(полей / колонок) + длинные поля (каждое = своя строка)
высота строки rof = 16 (метка body-xs) + 4 + 20 (значение body-m) = 40
высота тела тайла = Σ строк + 16×(строк−1)
```

Высоты «тяжёлых» вставок, которые ломают ритм 40px: `badge--m` 32,
`chip--s` 24, ProgressBar с заголовком ~30, чиплист в 2 ряда ~56.

**Сравнивая тайлы (K6), сравнивай тела** — шапки одинаковы, если у обоих есть
`.tile__header`. Полная высота тайла = шапка (~50: padding 20/10 + заголовок) +
тело + `--tile-pad-bottom` 24. Это важно, когда рядом стоят обычный тайл и
`tile--headless`: у них разные шапки, и тела сравнивать уже нельзя.

**Сколько строк займёт длинное значение** (нужно для K2.1):

```
символов в строке ≈ ширина ячейки / 8      (body-m 16px, кириллица)
строк значения    = ceil(длина значения / символов в строке)
```

Считать надо по **максимально возможной** длине значения, а не по демо-строке:
комментарий на 61 символ — одна строка, тот же комментарий на 250 — четыре,
и тайл вырастает на 60px, ломая ряд.

Проверь по факту: значения токенов — в `DS-IBP/styles/tile.css`, `DS-IBP/styles/spacing.css`,
`DS-IBP/styles/typography.css`; формула — ориентир, а не замена чтению.

## Блокеры композиции

| # | Проверка | Как выявить |
|---|---|---|
| K1 | **Нет пустоты у правой кромки тайла.** Мерится **воздух от правого края самой широкой пары «метка + значение» в последней колонке до внутренней границы тайла** — не заполненность ячейки. Дефект, когда воздух **больше половины ширины тайла И больше 250px** одновременно (два порога, оба обязательны: доля без абсолюта шумит на узких тайлах). **Исключение: одноколоночный тайл шириной 3–4 колонки под K1 не проверяется** — его ширина задана рядом, а не контентом. **Приоритеты: K6 старше K1, K1 старше K5** (см. «Конфликты правил») |
| K2 | **Длинное поле (описание, комментарий, адрес, перечень) занимает ряд целиком**, не стоит рядом с коротким | найти длинные поля, проверить, что каждое на всю ширину |
| K2.1 | **Длинное поле не живёт в узком тайле (3–4 колонки) без ограничения строк** — иначе реальное значение на 250 символов раздует тайл и разорвёт ряд | есть длинное поле в узком тайле → должен быть clamp с тултипом либо тайл шире |
| K3 | **В одном ряду поля сопоставимого класса** — короткое с длинным не смешано | |
| K4 | **Ширина тайла соответствует объёму.** 3–5 полей → 4 колонки · 6–9 → 6 · 10+ → 8 · таблица/график → 12. **Наличие длинного поля само по себе поднимает тайл минимум до 8** (условия независимы: выполняется любое — берётся большая ширина) | посчитать поля и отдельно проверить наличие длинных |
| K5 | **Колонок полей столько, сколько влезает:** `floor(внутренняя ширина тайла / 240)`, максимум 4. Ячейка ýже 240px — колонок меньше; ячейка шире ~600px под текстовое значение — колонок больше (иначе строка вылезает за 50–75 символов). **Одна колонка в тайле шириной 4+ колонки сетки — дефект:** в `col-4` (~555px внутри) помещаются две | посчитать ячейку: `(внутри − (кол−1)×16) / кол` |
| K6 | **Соседи в ряду сопоставимы.** Мерить **строками и высотой, не числом полей.** Дефект, когда: расхождение **больше 1,5× по строкам И больше 80px**, либо **больше 120px независимо от строк**. Отношение строк без абсолюта не считается: на тайле из 3 строк одна лишняя строка даёт 1,33× при копеечных 40px | посчитать по формулам ниже высоту тела каждого тайла ряда |
| K7 | **Однотипные величины оформлены одинаково.** Два подслучая, оба дефект: (а) одна по природе величина оформлена по-разному (перечень сотрудников — где чипами, где текстом); (б) разные по природе величины оформлены одинаково так, что читаются как сравнимые (доля выполнения и качественная оценка на одинаковом треке) | |
| K8 | **Режим соответствует экрану:** чтение — многоколоночно; форма ввода — одна колонка (кроме парных коротких полей) | |
| K9 | **Блоков в зоне не больше 7–8. Полей в тайле:** до 10 — норма · **11–12 — замечание** (нужна подгруппировка или разбиение) · **13+ — блокер**. Подгруппировкой считаются: подзаголовок внутри тайла, увеличенный зазор между группами (24 против 16), разделитель, разбиение на два тайла. **Совпадение смысловых пачек со строками сетки подгруппировкой не считается** — при одинаковом зазоре читатель видит однородные строки, а группировка держится только пока состав полей не менялся | считать поля, отдельно смотреть, не разорваны ли смысловые пачки между строками |
| K10 | **Ключевое для роли видно без скролла** — идентификация объекта и его состояние в первом экране. **Идентификатор при этом непротиворечив:** код и название совпадают в крошках, заголовке и активном пункте меню | |
| K11 | **Отклонение порядка блоков от ТЗ обосновано** в `screen.md`. Обоснование должно быть **правдивым**: таблица раскладки в `screen.md` (ширины, число полей, число колонок, состав рядов) сверяется с фактической разметкой | сверить таблицу из `screen.md` с разметкой построчно |
| K13 | **Нет добавленных сущностей.** Индикатор (прогресс-бар, шкала, диаграмма, светофор) стоит только там, где ТЗ говорит о доле, проценте или динамике. Качественная оценка из справочника («Высокая», «Средняя») подаётся так же, как соседние справочные значения — чипом или текстом. **Признак дефекта: чтобы нарисовать индикатор, понадобилось число, которого в ТЗ нет** | сверить каждый индикатор с формулировкой поля в ТЗ |
| K12 | **Адаптивные правила не мертвы:** `@container`-правило, перебитое инлайн-стилем на том же элементе, никогда не сработает — узкая раскладка не отработает | найти `@container` и проверить, нет ли инлайн-`style` на тех же свойствах |

## Замечания (не блокируют, но фиксируются)

| # | Проверка |
|---|---|
| З1 | Ряд не обязан быть плотно набит, но три ряда подряд с одиноким полем — повод пересобрать |
| З2 | **Выравнивание чисел вправо — правило таблиц, не карточек.** В таблице колонка сумм выравнивается по правому краю (разряды сравнимы взглядом). В сетке полей карточки, где метка стоит над значением, выравнивание вправо рвёт левый край меток — там значения остаются слева. Разное выравнивание в таблице и в карточке — норма, не дефект |
| З3 | Действия блока (переход/редактирование) единообразны: одинаковые действия — одинаковые иконки и места |
| З4 | Переход во внешнюю систему визуально отличается от перехода внутри продукта |
| З5 | Единицы измерения и формат чисел/дат единообразны по всему экрану. **Единица стоит в одном и том же месте:** либо во всех метках тайла, либо во всех значениях — не «Объём, шт. / 300 000» рядом с «Номинал / 1 000 руб.». В таблице единица — в заголовке колонки, не в каждой ячейке |

## Конфликты правил — порядок старшинства

Правила иногда тянут в разные стороны. Порядок разрешения:

**K6 > K1 > K5**

- **K6 старше K1.** Если добавление колонки выводит тайл из сопоставимости с
  соседом по ряду — колонку не добавляют, остаточная пустота идёт замечанием.
  Ровный ряд важнее идеально набитого тайла.
- **K1 старше K5.** Если по таблице ширин положена 1 колонка, но значения
  короткие (счётчик, чип, дата, код) и у правой кромки пусто — колонок дают
  больше, чем велит таблица.

Конфликт, разрешённый в пользу старшего правила, **фиксируется замечанием**
с обоими числами, чтобы решение было видно и не переигрывалось вслепую.

## Принятое отклонение — не переоткрывать каждый прогон

Отклонение от любого правила K1–K12, которое **записано в `screen.md`
с обоснованием**, понижается до замечания и помечается так:

```
K7 (принято, screen.md §8) — два ProgressBar в «Стадии»…
```

Условия понижения (все обязательны):

1. обоснование есть в `screen.md` и объясняет **почему**, а не констатирует факт;
2. обоснование **правдиво** — сверено с разметкой (это K11, он становится
   метаправилом для всех остальных кодов);
3. отклонение не создаёт новых дефектов у соседей.

Не выполняется хоть одно — пункт остаётся блокером.

Смысл: гейт не должен каждый прогон заново оспаривать решение, которое уже
принято осознанно и записано. Но и молча принять недокументированное отклонение
он не может.

## Что дефектом НЕ является

**Содержание демо-данных на макете — «рыба».** Имена, суммы, даты, названия
организаций подставлены для наглядности и ничего не значат. Не поднимай вопросы
вида «одно ФИО стоит в двух полях — это дубль?», «почему у двух полей одинаковое
значение», «правдоподобна ли эта сумма». Это не дефекты и не вопросы к
постановщику — это шум, который съедает ход приёмки.

Проверяется **форма**, а не содержание:

| Проверяем | Не проверяем |
|---|---|
| формат даты, разряды в числах, единицы измерения | конкретные значения дат и сумм |
| единообразие оформления однотипных полей | совпадают ли значения в разных полях |
| правдоподобие **длины** значения (не поместится ли реальное) | правдоподобие смысла значения |
| есть ли данные вообще (не заглушка ли) | какие именно данные |

Два исключения:

1. **Демо-значение ломает раскладку** (не влезает в ячейку, переносится в три
   строки). Тогда дефект в раскладке, и формулировать надо именно так, а не
   «данные неверные».
2. **Хром экрана — не демо-данные.** Крошки, заголовок страницы, активный пункт
   меню, название объекта в шапке — это навигация, а не наполнение. Их
   согласованность между собой проверяется всегда (K10): один объект не может
   называться двумя разными кодами в трёх местах первого экрана.

## Формат вывода

```
ВЕРДИКТ: PASS | NEEDS-WORK

БЛОКЕРЫ КОМПОЗИЦИИ
K4 — тайл «Условия выпуска»: 11 полей на 12 колонках в 4 колонки → подписи
     переносятся; дать 8 колонок и 3 колонки полей

ЗАМЕЧАНИЯ
З3 — ...

ЧТО ХОРОШО
- ...
```

Каждая претензия — с именем блока и конкретным числом (строк, пикселей,
колонок), а не «выглядит неаккуратно». Претензия без числа или без имени блока
дефектом не считается.

**Зависимые дефекты помечай.** Один дефект часто виден в двух проекциях (пустота
в тайле → несопоставимость ряда) и чинится одной правкой. Пиши
`K6 — … (следствие K1)` и ставь такие пункты подряд, чтобы их не чинили дважды
и по-разному.

Причина может стоять **в другом ряду и под другим кодом**: отсутствие clamp'а на
длинном поле (K2.1) сегодня не видно, а завтра, на реальном значении, ломает
сопоставимость ряда (K6). Такие связи тоже помечай — иначе «безобидное»
замечание чинят последним, уже после того, как оно выстрелило.

Раздел «Что хорошо» обязателен: он показывает, какие решения не надо ломать при
починке.

## Частые дефекты и их починка

| Симптом | Причина | Починка |
|---|---|---|
| Экран — длинная лента, много скролла | все тайлы на 12 колонок | раздать 4/6/8 по объёму |
| В тайле пусто справа | ширина завышена / колонок полей мало | сузить тайл или добавить колонок |
| Подписи полей переносятся в 2 строки | колонок полей много | уменьшить до 2–3 |
| Один тайл в ряду выглядит полупустым | несопоставимые соседи | поменять пару или дать высокому свой ряд |
| Описание обрезано или ломает сетку | длинное поле в общем ряду | на всю ширину ряда |
| Экран «рябит» | однотипные данные оформлены по-разному | привести к одному компоненту и варианту |

## Композиция конструктора (страницы документации, паттерн docs-split)

Проверяется на страницах `DS-IBP/pages/**` с `main.page.ds-split` (вкладка
«Конструктор»). Механика — в `screen-review` (К8–К11); здесь — только
визуальная композиция колонок конструктора:

| # | Проверка |
|---|---|
| КК1 | **Левая колонка (`.ctl-col`) с равномерными отступами.** Поля не растянуты по высоте (признак остатков `.pg__controls .ctl { flex:1 1 … }` в `<style>`); зазор между полями ровный (gap из docs-split.css). Вертикально растянутые поля с большими промежутками — дефект |
| КК2 | **Свитчи в правой колонке с непустой, читаемой подписью.** Пустой текст у свитча (признак подписи не из `.lbl`) — дефект. Свитчи одной колонки выровнены по левому краю, подписи не переносятся в 2 строки |
| КК3 | **Группировка читается:** заголовок группы (`.pg__grouphead`) стоит над своими контролами, а не стопкой вверху без содержимого; разделитель группы не оторван от группы |
| КК4 | **Баланс колонок не вызывает вопросов.** Не-бинарные селекты и инпуты слева; если справа только один-два свитча, а слева восемь полей — допустимо (механизм раскладки), но зазор/выравнивание не должны выглядеть случайными |

Претензия — с именем страницы и описанием видимого симптома («поле X в
левой колонке растянуто на всю высоту, под ним пусто ~40px»). Номер строки —
по `<style>` или по хелперу page.js, где это задаётся.

Задокументированные отклонения (журнал уроков `lessons.md`: чекбоксы `.cb`
и слайдеры в левой колонке, нативные segctrl) — не переоткрывать.
