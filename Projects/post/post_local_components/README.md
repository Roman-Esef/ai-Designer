# post_local_components — локальные компоненты направления Post

Модули, из которых собираются страницы направления: тайлы со своими модальными окнами и
прочие составные части экрана. Компоненты дизайн-системы сюда не копируются — здесь живёт
только то, чего в `DS-IBP/` нет и что принадлежит направлению.

## Зачем

Страница не собирается каждый раз с нуля и не держит в одном HTML-файле всё про все свои
объекты. Страница знает **перечень модулей**, которые в неё входят; сам модуль правится
точечно в собственных файлах, а страница подхватывает изменения. Если правка на странице
касается конкретного модуля — правится модуль, а не страница.

## Устройство

- Папка на модуль: `post_local_components/<Модуль>/`.
- Внутри — разметка модуля, его паспорт, его CSS и модалки: всё, что принадлежит только ему.
- Правила заполнения — страница ДС «Локальные компоненты»
  (`DS-IBP/pages/patterns/LocalComponents.html`), заготовка — `DS-IBP/templates/local-component/`.

| Файл | Когда появляется |
|---|---|
| `<Модуль>.html` | сразу: фрагмент разметки с одним корневым элементом, без `<html>`/`<link>`/`<script>` |
| `<Модуль>.md` | сразу: паспорт; неизвестное пишется как `не решено (ДД.ММ.ГГГГ)`, не догадкой |
| `<Модуль>.css` | когда у модуля появляется внутренняя раскладка |
| `<Модуль>.doc.html`, `fixtures.json`, `baseline.png`, `CHANGELOG.md` | когда модуль наполняется содержимым |

## Механика подключения — ассемблер

Выбрана 19.09.2026. Страница ставит на место модуля метку, а место в сетке задаёт классом
на самой метке:

```html
<ds-include src="../post_local_components/TileKNR/TileKNR.html" class="col-3 colw-6"></ds-include>
```

Собирает страницу `../assemble.mjs`:

```bash
node Projects/post/assemble.mjs          # все источники направления
node Projects/post/assemble.mjs <файл>   # один
```

Источник `<имя>.html` превращается в самодостаточный `<имя>.preview.html` — **открывают
двойным кликом именно его**. После правки любого модуля или источника — пересобрать.

**Почему сборка, а не рантайм.** В ДС есть `scripts/ds-include.js`, который делает то же
самое в браузере, но он тянет фрагмент через `fetch`, а `fetch` по `file://` не работает.
Страницы здесь открываются двойным кликом, поэтому вшивание делается до открытия.
Контракт у ассемблера тот же, что у рантайма: `id` и `class` с метки переносятся на корень
фрагмента (прежнее значение заменяется, а не дублируется вторым атрибутом),
`state`/`mode` становятся `data-state`/`data-mode`, а CSS модуля — файл рядом с `src` —
подключается линком в `<head>` (атрибут `css="…"` переопределяет путь, `css="none"`
отключает).

Инструменты приёмки фрагмент экраном не считают: `layout-check` и `ds-lint-cli` печатают
на нём `ПРОПУЩЕН:` и проверяют собранный файл. Определение фрагмента — в
`.opencode/skills/screen-review/tooling/fragments.mjs`.

## Связи между модулями

Модули не изолированы, и это часть замысла:

- Сущность из тайла дерева продуктов переносится в соседний тайл и отображается там; в
  дереве она остаётся, но меняет вид — видно, что она вложена в другой тайл.
- Признак в одном тайле (например, отмеченный чекбокс) управляет тем, показывается ли
  другой тайл — на этой же или на другой странице. Значит, признак принадлежит сделке, а
  не странице: система должна знать, что у конкретной сделки есть флаг, влияющий на
  конфигурацию другого экрана.

Модель хранения таких признаков и способ, которым модули узнают друг о друге, **не
определены** — это следующее решение после механики подключения.

13 модулей страницы сделки (`../deal_post/Deal.html`). Все — в состоянии заглушки
(`data-state="empty"`): оболочка есть, состав полей не согласован.

| Модуль | Где стоит |

| `TileProjectInfo` | Общая информация, третий ряд (12, опциональный) |
| `TileDealSetup` | Общая информация, правая колонка 320px |

| `TileEpsVbsImpact` · `TileFinMetrics` | таб «Финансовые данные», второй ряд (6 + 6) |

| `TileCollaterals` | таб «Обеспечения» (12) |
