# post_local_components — локальные компоненты направления Post

Модули, из которых собираются страницы направления: тайлы со своими модальными окнами и
прочие составные части экрана. Компоненты дизайн-системы сюда не копируются — здесь живёт
только то, чего в `DS-IBP/` нет и что принадлежит направлению.

## Зачем

Страница не собирается каждый раз с нуля и не держит в одном HTML-файле всё про все свои
объекты. Страница знает **перечень модулей**, которые в неё входят; сам модуль правится
точечно в собственных файлах, а страница подхватывает изменения. Если правка на странице
касается конкретного модуля — правится модуль, а не страница.

## Витрина кита

`index.html` — одна точка входа в кит: слева навигация по категориям, справа карточки
группами. С неё открывается витрина любого компонента, и та же панель стоит в самой
витрине — переход между компонентами без возврата на обзор. Требование — правила
локальных компонентов, раздел «Категории и витрина кита».

Список компонентов **не ведётся руками на страницах**: он лежит в `kit.js`
(`window.PostKit`), рисует его `kit-nav.js`. Завели компонент — добавили строку в `kit.js`;
копии списка в витринах нет. Спека страницы — `index.screen.md`.

**Категории направления Post:** Общие · Сделка · Инструменты · Отчёты · Другое. Показываются
все пять, в том числе пустые — по ним видно, куда класть новый компонент. Категория в
`kit.js` обязана совпадать с полем `category` паспорта. У других команд список свой.

**Страница компонента** собрана по тому же паттерну, что страницы компонентов ДС: сплиттер с
живым демо сверху, три таба (Конструктор · Документация · Код) и якорный TOC справа. Каркас
и табы держит слой ДС (`styles/docs-split.css` + `scripts/docs-split.js`, оба линкуются явно —
в барель `ds.css` они не входят), контролы конструктора создаёт `kit-docpage.js`. Эталон
структуры — `.opencode/skills/docs-split/references/skeleton.md`, проверка —
`docs-split.mjs check <файл>`.

**Что пишется на странице компонента** (решение человека 21.09.2026):

- **Во вкладке «Документация» — только описание и поведение компонента.** Классы, атрибуты,
  события и пути к файлам, «кто и когда решил», почему не взят другой компонент — не
  пишутся: это место паспорта, журнала и вкладки «Код». Если такая подробность нужна на
  странице, человек скажет явно.
- **«Из чего собрана» — таблица**, а не абзац: колонки «Компонент» · «Что делает в
  <компоненте>», по строке на компонент ДС или локальный компонент. По таблице сразу видно,
  сколько частей и каких. Образец — `TileKNR/TileKNR.doc.html`.
- **Последний раздел — «Бэклог»**, как на страницах ДС (`section[data-screen-label="Backlog"]`
  с `.panel > ul.rules`): чего документации не хватает, словами продукта. Наполняется из
  «Открытых вопросов» паспорта.
- **Конструктор** — по правилу ДС (`ds-rules.md` §11): да/нет — свитч, 2–3 варианта —
  ButtonGroup, 4 и больше — список; пустая колонка не рисуется. Все выборы `kit-docpage.js`
  создаёт селектами, превращает их `docs-split.js`. Над свитчем и ButtonGroup лейбла нет,
  поэтому подпись свитча и тексты вариантов самодостаточны («Узкая колонка», а не «Узкая»).

**Артефакты.** Модальное окно, панель или поповер компонента — не компонент: в плоском списке
кита их нет. Артефакт объявляется полем `artifacts` в записи `kit.js`, получает свой паспорт
и свою страницу рядом с компонентом-владельцем, а в панели становится под-пунктом аккордеона
под ним. Связь двусторонняя: `opens` в паспорте компонента, `artifactOf`/`opensFrom` — в
паспорте артефакта.

**Пункт-аккордеон не ссылка.** `ds-nav-panel.js` перехватывает клик по `.nav__item--acc`,
поэтому у компонента с артефактами первым под-пунктом идёт «Обзор» — его собственная
страница. Без этого на неё из панели не попасть.

**Витрина, которая показывает внутри себя другой компонент или своё окно, собирается
ассемблером**: у неё есть источник `<Имя>.doc.html` и результат `<Имя>.doc.preview.html`.
Открывают и указывают в `kit.js` именно результат. Витрина без меток остаётся одним файлом.

## Устройство

- Папка на модуль: `post_local_components/<Модуль>/`.
- Внутри — разметка модуля, его паспорт, его CSS и модалки: всё, что принадлежит только ему.
- Правила заполнения — страница ДС «Локальные компоненты»
  (`DS-IBP/pages/patterns/LocalComponents.html`), заготовка — `DS-IBP/templates/local-component/`.
  **Эта страница читается целиком** — перед тем, как заводить модуль или
  планировать правку. Она источник требований, а не справка: греп по ней
  находит то, что уже знаешь, и молчит о том, чего не знаешь. Запрет §4
  `ds-rules` на чтение страниц ДС целиком её не касается — исключение названо
  там же.

| Файл | Когда появляется |
|---|---|
| `<Модуль>.html` | сразу: фрагмент разметки с одним корневым элементом, без `<html>`/`<link>`/`<script>` |
| `<Модуль>.md` | сразу: паспорт; неизвестное пишется как `не решено (ДД.ММ.ГГГГ)`, не догадкой |
| `<Модуль>.css` | когда у модуля появляется внутренняя раскладка |
| `<Модуль>Modal.html`, `<Модуль>Confirm.html` | модалки модуля: у фрагмента один корневой элемент, поэтому каждый скрим — свой файл и своя метка `ds-include` в конце `body` экрана |
| `<Модуль>.js` | только если модулю нужно поведение, которого нет в рантаймах ДС. Ассемблер `.js` НЕ подключает — тег ставит экран сам, после `ds.js` |
| `<Модуль>.doc.html`, `fixtures.json`, `baseline.png`, `CHANGELOG.md` | когда модуль наполняется содержимым |

## Механика подключения — ассемблер

Выбрана 19.09.2026. Страница ставит на место модуля метку, а место в сетке задаёт классом
на самой метке:

```html
<ds-include src="../post_local_components/TileKNR/TileKNR.html" class="col-3 colw-6"></ds-include>
```

Собирает страницу `../assemble.mjs`:

```bash
node Projects/post/assemble.mjs          # все источники направления
node Projects/post/assemble.mjs <файл>   # один
```

Источник `<имя>.html` превращается в самодостаточный `<имя>.preview.html` — **открывают
двойным кликом именно его**. После правки любого модуля или источника — пересобрать.

**Почему сборка, а не рантайм.** В ДС есть `scripts/ds-include.js`, который делает то же
самое в браузере, но он тянет фрагмент через `fetch`, а `fetch` по `file://` не работает.
Страницы здесь открываются двойным кликом, поэтому вшивание делается до открытия.
Контракт у ассемблера тот же, что у рантайма: `id` и `class` с метки переносятся на корень
фрагмента (прежнее значение заменяется, а не дублируется вторым атрибутом),
`state`/`mode` становятся `data-state`/`data-mode`, а CSS модуля — файл рядом с `src` —
подключается линком в `<head>` (атрибут `css="…"` переопределяет путь, `css="none"`
отключает).

Инструменты приёмки фрагмент экраном не считают: `layout-check` и `ds-lint-cli` печатают
на нём `ПРОПУЩЕН:` и проверяют собранный файл. Определение фрагмента — в
`.opencode/skills/screen-review/tooling/fragments.mjs`.

**Витрина проверяется профилем, а не пропускается.** У неё нет каркаса экрана, поэтому
правила каркаса к ней неприменимы — сенсор печатает строку `ПРОФИЛЬ:` и список
пропущенных правил, а всё остальное (классы, иконки, ссылки, хуки рантаймов) проверяет
как на экране. Структуру самой витрины держит
`docs-split.mjs check` — гейт зовёт его для любой страницы с каркасом `ds-split`, в том
числе отсюда. До 21.09.2026 витрина пропускалась целиком, и три дефекта каркаса дошли
до человека при зелёном гейте.

## Связи между модулями

Модули не изолированы, и это часть замысла:

- Сущность из тайла дерева продуктов переносится в соседний тайл и отображается там; в
  дереве она остаётся, но меняет вид — видно, что она вложена в другой тайл.
- Признак в одном тайле (например, отмеченный чекбокс) управляет тем, показывается ли
  другой тайл — на этой же или на другой странице. Значит, признак принадлежит сделке, а
  не странице: система должна знать, что у конкретной сделки есть флаг, влияющий на
  конфигурацию другого экрана.

Модель хранения таких признаков в целом **не определена**. Определён первый случай —
состав участников сделки и её КНР (21.09.2026): его держит `CounterpartiesStore`
(`../data/counterparties-store.js`), сохраняет адаптер `PostApi` (`../data/post-api.js`),
контракт — `../data/API.md`. Окно КНР правит состав, тайл «КНР» и колонка «КНР» реестра
его читают. Следующие признаки сделки — по тому же образцу: стор направления + адаптер,
модули друг друга не знают.

## Режим правки

Режим прав приходит на модуль атрибутом `data-mode` и бывает двух видов: `edit` — действия
правки видны, `view` — они не рисуются вовсе (а не выключаются). Вид каждого режима держит
собственный CSS модуля, по образцу шаблона ДС (`templates/local-component/Component.css`).
Режим выставляет страница, модуль его не вычисляет.

Статус сделки сильнее роли. В статусах «Активная», «Погашена», «Ожидает подтверждения» и
«Подтверждение изменений» правка сущностей сделки невозможна, и страница ставит `view` всем
модулям при любой роли — правило живёт в `DealsStore.isEditable` (`../data/deals-store.js`).
Основание — «Текущий портфель.md» («В активной сделке нельзя редактировать сущности») и
решение человека 21.09.2026.

Выключенного действия с подсказкой-причиной нет: запрет по статусу — это тот же «Только
просмотр». Так же говорят правила ДС для локальных компонентов с версии 1.005.

## Состав

13 модулей страницы сделки (`../deal_post/Deal.html`) плюс один переиспользуемый.
Наполнены два: `TileKNR` и `CardCounterparty` (20.09.2026). Остальные 12 — заглушки
(`data-state="empty"`): оболочка есть, состав полей не согласован.

`TileKNR` — образец предметного модуля: фрагмент держит все состояния сразу, а показывает
нужное собственный CSS по `data-state` / `data-mode`. `CardCounterparty` — образец
переиспользуемого: фрагмент отдаёт `<template>`, а карточки по нему рисует потребитель из
своего стора.
