# Задача: обвязка агента — работы до реструктуризации

## 0. Почему эта задача идёт первой

Реструктуризация в три репозитория проверяется **одним инструментом** — гейтом.
Каждый её шаг заканчивается строкой `ВЕРДИКТ:`, и на неё опирается решение
«шаг закончен, идём дальше». Значит, до начала реструктуризации гейт обязан
быть честным.

Сейчас он честен не везде. Проверено прогонами:

| Где ложный сигнал | В чём он |
|---|---|
| `vendor-scan` | образец абсолютного пути написан только для windows-формы. Путь `/Users/…` не ловится **вообще** — то есть правило владельца «в файлах нет путей с машины автора» на этой машине не охраняется ничем |
| сторож `check` | обходит `.opencode/` и корневой `AGENTS.md`. Документ, вынесенный в `docs/`, выпадает из-под правил, которые сам пересказывает — находка `Л-ВЛАДЕЛЕЦ` исчезла не потому, что дублирование убрали, а потому что файл переехал |
| `gate --full` | **всегда** `FAIL (3 из 115)`. «Полный гейт зелёный» как критерий приёмки не работает ни для чего |

Если начать реструктуризацию до починки, каждый её шаг будет сверяться с
инструментом, который в трёх местах говорит неправду. Отсюда порядок: сначала
эта задача, потом `docs/restructure-3-repos.md`.

Вторая причина: реструктуризация двигает файлы десятками. Всё, что в обвязке
держится на литералах путей и на ручном пересказе, в этот момент ломается
тихо. Дешевле убрать лишнее и починить сторожей на неподвижном дереве.

---

## 1. Как исполнять

1. **Один шаг — один коммит.** Откат должен быть дешёвым.
2. **После каждого шага — гейт.** Красный гейт — шаг не закончен.
3. Шаги У1–У6 механические, исполняются подряд. Шаги У7–У9 требуют **решения
   владельца** — если решения нет, шаг пропускается и записывается в §7 как
   открытый, но задача **не считается закрытой**.
4. У10 (документ процесса) — всегда последний: он описывает итог.
5. Сомнение — в §7, а не в догадку.

## 3. Что трогать не надо

Список важен не меньше списка правок: несколько решений работают и легко
ломаются «упрощением».

| Решение | Почему оставить |
|---|---|
| Приёмка отдельным агентом с `edit: deny` | приёмщик, который может править, перестаёт быть приёмщиком |
| Доказательство закрепления откатом на фикстуре | единственный способ отличить «правило записано» от «правило работает». Именно оно вскрыло дыру в `vendor-scan` |
| Категория «суждение» в покрытии (20 из 70) | честно объявленная граница статики вместо имитации проверки |
| Правка по якорю `#sec:*` вместо перечитывания экрана | замерено: 20 900 токенов против 96 700 на трёх кругах правок |
| Вердикт читается строкой `ВЕРДИКТ:`, а не кодом выхода | подстановки и пайпы перезаписывают код выхода |
| `ДОЛГ:` — старый красный не краснит вердикт | без этого `FAIL` быстро перестал бы что-то значить |
| Задание субагенту как самостоятельный документ из четырёх частей | субагент не видит разговор с человеком; это единственный канал |

### У1 · `vendor-scan`: закрыть дыру абсолютных путей

**Зачем.** Сторож обещает ловить «абсолютные пути с машины автора», но образец
написан только для windows-формы (`C:\Users\…`). Работа идёт на macOS, значит
правило не охраняется. Проверено: файл со строкой
`/Users/someone/Work/secret-project/file.md` сторож не видит — вердикт «чисто».

Это хуже отсутствия сторожа: правило выглядит охраняемым, и при написании
документов на него полагаются.

**Что сделать.**
1. Добавить в `PATTERNS` образец posix-формы. Проверено на сегодняшнем
   репозитории: ложных срабатываний **ноль**, безопасно включать сразу.
   ```js
   { re: /(^|[\s"'(=])\/(Users|home)\/[^\/\s"'`]+\//, what: 'абсолютный путь с машины автора' },
   ```
   Образец собирается склейкой, как остальные, — иначе сторож найдёт сам себя.
2. Добавить `--selftest` по образцу `agent-config.mjs`: временное дерево, пара
   случаев на каждую форму пути (posix, windows) и чистый случай.
3. Подключить `vendor-selftest` шагом гейта.

**Проверка.** `vendor-scan --selftest` зелёный. Временный файл с
`/Users/…`-путём даёт FAIL, без него — «чисто».
**Готово когда.** Обе формы пути ловятся, починка доказана откатом.
**Откат.** `git revert`.

### У3 · Три красных экрана: разделить настоящий долг и пробел модели

Полный гейт всегда красный. Разбор показал два разных случая.

`Projects/post/mainPage/index.html` (спека, строки 122, 137, 149) и

**Зачем.** Б32 — «спека описывает состояние экрана, история живёт в git».

**Проверка.** Сенсор на обоих экранах зелёный.

#### У3б · `MaterialReport.html` — пробел в модели, а не дефект

**Зачем.** Экран падает на Б5 (нет `.nav-layout`, `.nav`, `.screen`,
`.crumbs`, `main.screen__content`) и Б6 (один `h1`). Но это **не экран
приложения**: это лист отчёта — документ на «бумаге», который пользователь
получает файлом, без навигации и хлебных крошек. Каркас приложения ему не
нужен и не должен быть нужен.

Сенсор считает экраном любой `.html` в папках проектов и концептов. Отличать
фрагмент от экрана он уже умеет (`fragments.mjs`), а третьего вида — документа
— в модели нет. Поэтому здесь два честных выхода и один нечестный.

**Что сделать** (выбор владельца, §7, вопрос 1):
- **вариант А (рекомендуется):** завести вид экрана. `kind: document` в
  frontmatter спеки, сенсор не применяет Б5 и Б6 к такому файлу, а применяет
  свой, меньший набор. Пара фикстур доказывает, что вид работает и что
  обычный экран без каркаса по-прежнему краснеет;
- **вариант Б:** признать, что документ обязан жить внутри каркаса, и привести
  экран к нему.

Нечестный выход — добавить файл в исключения списком. Это снимет красноту, но
следующий документ снова упрётся в то же место.

**Проверка.** `gate --full` зелёный.
**Готово когда.** Полный гейт можно использовать как критерий.
**Откат.** `git revert`.

### У7 · Права: конфиг против README — **решение владельца**

**Зачем.** В конфиге `edit: {"*": "allow"}`, `bash: {"*": "allow"}` (кроме
`rm`, `git push`, `git reset`), `webfetch` и `websearch` разрешены. README
обещает запись только в папку концептов, выключенный `webfetch` и
подтверждение на небезопасные команды. Сужение есть только во frontmatter
четырёх своих агентов — то есть встроенные вспомогательные агенты, которых
ведущий может вызвать, работают с глобальными правами и могут править файлы
ДС.

Это тот же класс, который обвязка ловит у других: правило разошлось с
реальностью. Перед реструктуризацией это особенно важно — агент будет
массово двигать файлы, и границы записи должны быть теми, на которые
рассчитывает человек.

**Что сделать.** Привести в соответствие в ту сторону, которую выберет
владелец (§7, вопрос 2):
- **сузить конфиг** до того, что обещает README, либо
- **переписать README** под фактические права, явно назвав, что
  вспомогательные агенты могут править файлы ДС.

**Проверка.** README и конфиг описывают одно и то же. Гейт зелёный.
**Откат.** `git revert`.

Промежуточное состояние не оставлять: оно хуже обоих.

**Проверка.** Либо `/research` возвращает непустой отчёт с источниками, либо
ветки нет в дереве и в документе процесса.

### У9 · Смета контекста: калибровать или свернуть — **решение владельца**

**Зачем.** `calibration.jsonl` пуст: 0 замеров. Вердикты `OK` / `ВНИМАНИЕ` /
`РАЗБИТЬ`, по которым агент решает, дробить ли заход на сессии, опираются на
оценочные коэффициенты. Гейт печатает об этом `ВНИМАНИЕ` каждый прогон, и долг
не закрывается — напоминание, которое не приводит к действию, перестаёт
читаться.

**Что сделать** (§7, вопрос 4):
- **калибровать**: после следующих трёх заходов записать факт
  (`ctx-budget.mjs --calibrate --stage <этап> --fact <токенов>`). Реструктуризация
  даёт для этого естественный материал: пятнадцать шагов — это пятнадцать
  заходов; либо
- **свернуть**: если владелец считает, что смета не окупается, — заменить её
  правилом «экран больше ~800 строк дробится на этапы», а `ctx-budget`,
  `stages.json` и шаг гейта убрать.

Решение принимается **сейчас**, исполнение по варианту «калибровать» — по ходу
реструктуризации. Это единственный шаг задачи, который допустимо закрыть
решением, а не действием.

**Проверка.** Либо в `calibration.jsonl` появляются замеры, либо механики
сметы в ките больше нет и `ВНИМАНИЕ` исчезло.
**Откат.** `git revert`.

## 5. Критерии приёмки задачи

| # | Критерий | Чем проверяется |
|---|---|---|
| 1 | `gate --full` зелёный | одна команда |
| 2 | `vendor-scan` ловит обе формы абсолютного пути | `--selftest` + временный файл |
| 3 | Переезд документа между каталогами не снимает находок сторожа | перенести файл, `check` продолжает находить |
| 4 | `runs.jsonl` не растёт без предела | размер после десяти прогонов гейта |
| 5 | Ни один объявленный предел не превышен молча | `state` + искусственное превышение краснит |
| 6 | README и конфиг описывают одни и те же права | сверка вручную |
| 7 | В дереве маршрутизации нет ветки с заранее известным пустым результатом | `/research` либо работает, либо отсутствует |
| 8 | Документ процесса не пересказывает правила, у которых есть владелец | `check` зелёный + объём ~250 строк |
| 9 | Решение по смете принято и записано | §7, вопрос 4 закрыт |

**Только после выполнения всех девяти** начинается
`docs/restructure-3-repos.md`, шаг Ш0.
